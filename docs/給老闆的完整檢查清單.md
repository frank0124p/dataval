# 資料表上線安檢 — 完整檢查清單（白話版,逐條說明）

這份清單把工具**所有的檢查條件**逐條用白話說明。燈號規則:
🔴 **紅燈 = 查到就擋下,不能上線**;🟡 **黃燈 = 提醒改善,先放行**;
🔵 **藍燈 = AI 顧問建議,僅供參考,不影響過關與否**。
過不過關只由紅燈決定;AI 無權放行或攔人,同一張表怎麼檢查結果都一樣,可稽核。
（括號內的英文代號是系統內部的規則編號,方便同仁對照,報告時可略過。）

---

## 第〇關:進場資格審查——文件不齊,連檢查都不開始

送檢時必須繳齊**三樣東西**,缺一樣就退件,連報告都不會產生
（樣本資料為選繳,有繳能多做幾道「拿真資料驗證」的檢查）:

| 文件 | 白話說明 |
|---|---|
| ① 資料表設計圖（必繳） | 表格的正式定義:有哪些欄位、什麼格式（技術上叫 DDL） |
| ② 關聯說明書（必繳） | 這些表之間怎麼串、對應關係是一對一還是一對多。之後改動時「誰會被影響」全靠這份 |
| ③ 用途說明書（必繳） | 這批資料是什麼、給誰用、**每一列代表什麼**（這格必填——「一列到底是一張訂單還是一筆明細」講不清楚,後面所有統計都可能是錯的） |
| ④ 樣本資料（選繳） | 每張表附一份真實範例資料。「宣稱的對應關係、格式」要拿真資料驗證都靠它;沒繳不退件,只是這幾道檢查略過並註記 |
| ⑤ 加工 SQL（選繳） | 寬表（多來源整合出來的表）建議附上「實際怎麼加工出來」的 SQL,工具會比對「SQL 做的」與「說明書說的」是否一致 |

退件時會附一張清單,明確告訴設計者缺哪樣、格式哪裡不對,補齊即可重送。

## 第一關:🔴 紅燈檢查(共 21 項)——任一項不過,不能上線

### 甲、防「錢算錯」(4 項)

| # | 檢查項目 | 白話說明 |
|---|---|---|
| 1 | 全面禁用會有誤差的小數格式 (bp_no_float) | 電腦的「浮點數」格式先天有微小誤差,幾百萬筆加總後帳一定對不平。全表禁用,需要小數一律用精確格式 |
| 2 | 金額欄位強制精確格式 (bp_money_decimal) | 名稱含「金額、價格、成本、費用、餘額、營收、薪資」的欄位,再多查一層,確保沒有漏網 |
| 3 | 比對數字欄位與真實樣本 (structural_type_sample) | 設計圖說這欄是數字,就拿樣本資料驗證裡面真的是數字。「設計說一套、資料長另一套」在這關現形 |
| 4 | 對應關係拿真資料驗證 (RELATION.CARDINALITY_SAMPLE) | 關聯說明書宣稱「一位客戶對一筆訂閱」,就檢查樣本裡客戶是否真的只出現一次。宣稱一對一、實際一對多,報表金額會直接翻倍——說一套做一套,擋下 |

### 乙、防「資料接不起來」(6 項)

| # | 檢查項目 | 白話說明 |
|---|---|---|
| 5 | 串接欄位格式必須一致 (ssot_join_keys) | 兩張表都有「客戶編號」,一張存數字、一張存文字,串起來會默默對不到人且不報錯。跨表比對格式,不一致就擋 |
| 6 | 引用的表必須存在 (structural_fk_resolves) | 欄位名稱宣告要對到某張表(如 order_id 對訂單表),那張表卻不存在——引用落空,擋下 |
| 7 | 引用的上游表要真的存在 (LINEAGE.UPSTREAM_EXISTS) | 關聯說明書說「我引用正式區的客戶主檔」,就去正式區核對那張表真的在。引用幽靈表,擋下 |
| 8 | 引用的欄位要真的存在 (LINEAGE.COLUMN_EXISTS) | 表在,但引用的那個欄位不在（改名了、拼錯了）——一樣落空,擋下 |
| 9 | 引用兩端的格式必須相容 (LINEAGE.TYPE_COMPATIBILITY) | 上游存數字、你用文字去接,對不起來。兩端格式不相容,擋下 |
| 10 | 只能引用申報過的領域 (LINEAGE.DOMAIN_SCOPE) | 用途說明書寫「本表屬於客戶領域」,就不能偷偷引用沒申報的其他領域資料——依賴關係必須誠實申報 |

### 丙、防「同一件事有兩套說法」(4 項)

| # | 檢查項目 | 白話說明 |
|---|---|---|
| 11 | 每種資料只有一個官方版本 (ssot_authority) | 公司登記了「客戶資料的官方出處是客戶主檔」,其他表就不能自立門戶再建一份客戶資料。出現第二個「官方」,擋下 |
| 12 | 同一筆事實不准重複存 (ssot_fact_duplication) | 客戶 email 的擁有者是客戶主檔,別張表再存一份 email——改了一邊、另一邊還是舊的,必然出錯。重複承載,擋下 |
| 13 | 同一個概念全公司同一個名字 (PRODUCTION.NAMING_CONSISTENCY) | 正式區已經把「客戶」叫 customer,新表就不能叫 client 或 buyer。同概念異名,擋下 |
| 14 | 同一條關聯不准有兩種說法 (PRODGRAPH.CARDINALITY_CONFLICT) | A 表說「客戶對訂單是一對多」,你的新表對同一條關聯說「多對多」——兩種說法必有一錯,擋下,先把事實釐清 |

### 丁、防「看不懂、沒人敢動」(4 項)

| # | 檢查項目 | 白話說明 |
|---|---|---|
| 15 | 表名統一格式 (naming_table_snake_case) | 全公司表名同一種寫法(小寫加底線),資產才可預測、可被工具自動盤點 |
| 16 | 欄位名統一格式 (naming_column_case) | 同上,適用到每一個欄位。MonthlyPrice 這種寫法會被擋 |
| 17 | 每個欄位必須寫說明 (naming_columns_commented) | 沒有說明的欄位,半年後連原作者都看不懂。說明會自動彙整成全公司可查的資料字典,所以一個都不能少 |
| 18 | 料件主檔必備料號與版次 (plm_part_master_baseline)〔PLM 領域〕 | 製造領域的料件主檔必須有料號和版次欄位,否則物料清單無法引用、版本無法追溯 |

### 戊、防「查得慢、存得貴、系統性風險」(3 項)

| # | 檢查項目 | 白話說明 |
|---|---|---|
| 19 | 必須指定排序索引 (structural_order_by) | 沒有排序索引的表,每次查詢都像在沒目錄的倉庫翻遍所有貨架。必須指定 |
| 20 | 必須用正式倉儲等級的儲存引擎 (structural_engine_mergetree) | 資料庫有多種儲存方式,只有正式等級的那一族具備索引、合併、過期清理能力。臨時性引擎不准進正式資產 |
| 21 | 識別欄位不可允許空值 (structural_key_not_nullable) | 用來識別每一列的關鍵欄位若允許空白,去重與合併的邏輯會壞掉,還多耗儲存。擋下 |

另外三項紅燈屬同組:狀態欄位必須用省空間格式 (bp_lowcardinality_status)、
物料清單必須有用量欄位 (plm_bom_needs_quantity)〔PLM〕、
新表加入後不可讓全公司的依賴關係繞成一圈 (PRODGRAPH.CYCLE——A 靠 B、B 靠 C、
C 又靠 A,資料流成了雞生蛋蛋生雞;含正式區檔案損壞 SYSTEM.PRODUCTION_PARSE、
本表內部循環 LINEAGE.CYCLE)。

## 第二關:🟡 黃燈檢查(共 13 項)——提醒改善,先放行

| # | 檢查項目 | 白話說明 |
|---|---|---|
| 1 | 建議附建立/更新時間 (structural_audit_columns) | 每列資料「何時進來、何時被改」是查問題時的基本線索 |
| 2 | 用字要照公司詞彙字典 (naming_glossary) | 禁縮寫(cust、qty、amt、dt…)與同義字(client、buyer 應統一為 customer)。字典可持續增補 |
| 3 | 識別欄位命名以 _id 結尾 (naming_pk_suffix) | 可預測的命名讓人與工具都能自動推斷串接方式 |
| 4 | 避免使用系統保留字 (naming_reserved_words) | select、order 這類字當欄名,寫查詢時處處要特殊處理,易出錯 |
| 5 | 名稱不可過長 (naming_identifier_length) | 超過 64 字元的名稱不利閱讀,部分工具不支援 |
| 6 | 時間欄位要標時區 (bp_datetime_timezone) | 不標時區的時間,跨國/跨系統比較會錯 |
| 7 | 個資與金額不放同一張表 (ssot_pii_amount_split) | 混存讓權限難切(看金額的人不必看個資),外洩風險面變大 |
| 8 | 時間欄位不可設奇怪的固定預設值 (no_future_event_time) | 事件時間預設成某個固定日期,會汙染所有時間統計 |
| 9 | 疑似漏登記的資料主體 (SSOT.UNREGISTERED_SUBJECT) | 看起來自成一類、卻沒在公司登記簿上的資料,提醒補登記,並自動列入候選清單 |
| 10 | 與公司參考模型的欄位落差 (ERD.ENTITY_REFERENCE) | 公司的參考資料模型記載了這張表該有哪些欄位,送檢的設計缺了或鍵不對,提醒對齊 |
| 11 | 加工 SQL 與文件不一致 (DERIVATION.* 系列) | 附了加工 SQL 時:SQL 裡有的串接、說明書沒寫→提醒補;SQL 產出的欄位與設計圖對不上→提醒同步。防「文件說一套、程式做另一套」 |
| 12 | 端到端流程對照 (FLOW.* 系列) | 公司定義的業務流程圖裡,這張表落在哪個環節、上下游是誰,一併呈現;流程檔本身壞了也會提醒,不會靜默消失 |
| 13 | 送件資料本身的小毛病 (SYSTEM.* 系列) | 附件格式、設定檔的讀取問題等,逐項列在報告裡,不會被靜默吞掉 |

## 第三關:🔵 藍燈——AI 顧問建議(共 14 項,不影響過關)

規則查得了「字寫錯」,查不了「意思錯」。這一區由 AI 從語意面提問,
以「給設計者思考的問題」呈現,**不做結論、不影響判定**:

| # | 顧問項目 | 白話說明 |
|---|---|---|
| 1 | 命名語意 (naming_semantic) | 縮寫混用、兩個名字其實指同一個東西、名字與內容對不上 |
| 2 | 表的體質與最佳實踐 (best_practice_semantic) | 判斷這是交易表、名冊表還是事件表,各自該套哪些業界做法 |
| 3 | 官方出處候選 (ssot_semantic) | 找出「看起來有兩個官方版本」「疑似重複存放」的資料,提名進登記簿 |
| 4 | 設計主體是否成立 (CONCEPT.SUBJECT) | 更上位的提問:這批表作為一個資料主體,粒度、範圍、命名是否自洽 |
| 5 | 可能漏宣告的關聯 (LINEAGE.SUGGESTION) | 從欄位命名保守推測「這兩張表可能有關係」,請設計者確認後補進說明書 |
| 6 | 與設計圖示的差異 (LINEAGE.ER_SUGGESTION) | 若附了關聯示意圖,比對圖與實際定義的出入 |
| 7 | 改動影響範圍 (PRODGRAPH.IMPACT) | 你這張表在正式區有誰依賴,改動前的「爆炸半徑」清單 |
| 8 | 參考模型記載的表用途 (ERD.TABLE_PURPOSE) | 公司參考模型記載了這張表「是做什麼用的」,呈現在報告請設計者對照本次用法是否一致 |
| 9 | 建議版設計對照 (PROPOSAL.DDL) | 工具依公司參考模型**自動組出一版建議的串接 SQL 與表設計**,和送檢的設計並排對照——純建議,供設計者參考差異 |
| 10–13 | 製造領域四題〔PLM〕 | 物料清單結構是否自洽 (plm_bom_structural_integrity)、版本能否回答「當時有效的是哪一版」(plm_revision_versioning)、產品生命週期階段是否受控 (plm_lifecycle_stage)、工程變更是否可追溯 (plm_engineering_change) |
| 14 | 主檔治理〔FCM〕(fcm_master_data_semantic) | 主檔的唯一識別與官方出處是否清楚、屬性有無重複承載風險 |

## 第四關:上線之後的持續把關

| 機制 | 白話說明 |
|---|---|
| 問答收斂 | AI 顧問的提問會**先代填建議答案**,設計者只需驗證;答完重跑,報告只列「這輪與上輪的差異」,直到問題答完、紅燈全過(上限五輪,逐輪留檔可稽核) |
| 晉升制度 | 全部紅燈通過的表,才能由指令搬進「正式區」;不合規的表,工具直接拒絕,附上卡住的原因清單(可加開「問答未收斂也擋」) |
| 體檢證明 | 每張進正式區的表都附一份記錄:何時通過、用哪個版本的規則、檢查結果的存證編號——日後可追溯「當時憑什麼放行」 |
| 定期健檢 | 對整個正式區掃描:文件是否齊全、依賴有沒有斷掉、關聯宣告有沒有互相矛盾 |
| 舊表回診 | 規則升級後,自動列出「哪些表是用舊版規則通過的」,建議重驗——品質標準提高時,存量資產不會漏掉 |

## 收尾一句話

**紅燈 24 項擋住真金白銀的損失,黃燈 13 項持續拉高品質,藍燈 14 項讓 AI 當
顧問而不當法官;文件不齊不開檢,問答收斂才算完,上了線還有健檢與回診**
——這就是整套制度。
