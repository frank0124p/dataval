# 正式區複用（語意判讀）

## 目的

閘門只看得到**宣告出來的關聯**（relations.yaml 的三段式端點）——沒宣告就是
沒引用。但真正要問的是語意問題：**這個新主體要承載的事實，是不是正式區
已經有人承載了？** 同一件事各自建一份，跨域分析就永遠對不起來。

## 適用情境

正式區非空時的每個新 subject。可複用的資產與確定性候選（同名欄位）由工具
放進 prompt 的「正式區資產」區塊。

## 違反後果

同一事實出現多份來源，權威不明；下游 join 得到不一致的答案，且沒有人知道
該修哪一邊。設成 advisory 是因為「該不該複用」需要理解業務語意——
確定性的部分已由閘門 `PRODUCTION.REUSE` 提醒。

## 修正建議

該引用的補進 `relations.yaml`（`to: DOMAIN.table.col`）；確定不該引用的，
在問答區交代為什麼（例如粒度不同、是刻意的快照）。

## 卡控

```check-llm
對照 prompt 的「正式區資產」區塊，逐項判讀本主體與已核准主體的**語意**關係：

1. **同名欄位候選**：工具列出的同名欄位（如 customer_id）指的是同一個實體嗎？
   若是 → 提問「要不要改成引用正式區的權威表，而不是自己存一份？」
   若不是（同名不同義）→ 提問「命名撞名是否會誤導下游？」
2. **語意重疊（欄名不同也要看）**：本主體的表要承載的事實，是否已由某個
   已核准主體承載？例如本主體想做「客戶等級」，而正式區的客戶主檔已有——
   即使欄名不同，也要提出。
3. **只存鍵原則**：若本主體複製了外部權威的屬性（名稱、等級、聯絡方式），
   提問是否該改成只存鍵、屬性從權威表 join。
4. 判斷不出來就不要硬湊——寧可少一題，也不要把不相干的表湊成建議。

每題指出具體的表或欄位，用提問語氣，並附 proposed_answer 與 proposed_kind
（要改 relations.yaml／DDL 的填 structural 並註明 proposed_applied_to）。
```
